# The Supabase adapter

The second implementation of `MissionRepository`, and the reason the interface
exists. Everything above the data layer is written against the interface, so
which of the two adapters is in use is a configuration decision made in
`src/server/data/index.ts` and nowhere else.

```
getRepository()
  └─ appConfig.isMockData ? in-memory : supabase
```

There is no flag and no override. "Which database is this reading?" must not
be answerable differently in two places.

## Shape

| File | Holds |
| --- | --- |
| `supabase/adapter.ts` | Assembles the 24 repositories |
| `supabase/query.ts` | Tenant scoping, error handling, the `TenantFilter` seam |
| `supabase/client.ts` | `createAnonClient` (carries the caller's session), `createServiceClient` |
| `supabase/mapping.ts` | Row/column conversion, `numeric`-as-string handling |
| `supabase/audit-columns.ts` | Generated. Which tables carry which audit columns |
| `supabase/entity-tables.ts` | Which table an addressable `EntityType` lives in |
| `supabase/repositories/*.ts` | One module per repository, 255 methods |

Parameter types are never restated. Each module declares the interface type and
lets contextual typing supply the signatures, so `types.ts` stays the single
definition and a signature change cannot drift out of sync.

## A client factory, not a client

A Supabase client carries the caller's session in its cookie handlers, so it
belongs to one request. `getRepository()` is memoised for the process. The
adapter therefore takes `() => Promise<SupabaseClient>` and resolves it per
call; one client held in the singleton would serve every request as whoever
made the first one.

A consequence worth knowing: **a PostgREST builder is itself thenable**, so
returning one from an `async` method means `await` unwraps it and runs the
query. Every builder stays inside the method that built it.

## Two layers, and the seam that proves it

Reads and writes are scoped twice — by the adapter's own `organisation_id`
filter, and by row level security. The redundancy is the point.

`TenantFilter` exists so that can be tested. `createSupabaseRepository(client,
{ tenantFilter: "off" })` builds queries with no organisation predicate at all.
Isolation must still hold, because RLS is the second layer.
`tests/contract/rls-mutation.test.ts` asserts exactly that. **Nothing in the
application may construct a repository with the filter off.**

| Layer | Tested by | Runs as |
| --- | --- | --- |
| Adapter filter | `tests/contract/supabase.contract.test.ts` | service role (RLS bypassed) |
| RLS policies | `tests/database/rls.test.ts` | `authenticated`, real session |
| Both together | `tests/contract/rls-mutation.test.ts` | signed-in session, filter off |

## Generated files

`audit-columns.ts` is generated by applying every migration to a throwaway
Postgres and reading the result, rather than parsing SQL. Audit stamping is not
uniform — of 160 tables, 30 have `created_by`, 4 have `updated_by` and 63 have
`updated_at` — and a write layer that stamps unconditionally fails on the
majority of them.

```
npm run generate:audit-columns
```

`tests/unit/audit-columns.test.ts` regenerates it and fails on any difference.
The failure it prevents is silent: the insert succeeds, the row is anonymous,
and nothing reports a fault.

## The anonymous surface

Every policy in the product reduces to `is_org_member(organisation_id)`, which
is correct everywhere except the one path where the caller is a member of
nothing: a member of the public filling in a public form.

Migration `0029` teaches the database that rule rather than putting a
service-role key behind an unauthenticated endpoint — which would leave
application correctness as the only thing between the public and every row.

- `anon` may read a form that is `public`, `open`, unarchived and serving a
  published version, that version, and its fields. Nothing else — not
  submissions, not answers, not the organisation.
- Writes go through `public_form_submit`, a `security definer` function that
  resolves the form from the slug itself and takes each answer's label, type
  and **sensitivity from the field definition rather than the payload**. A
  caller cannot mark special category data as routine, because it never gets to
  state the classification.

`tests/database/public-forms.test.ts` checks all of it as the `anon` role.

## Running the database tests

`tests/database/*` build a throwaway Postgres, apply every migration and drive
it as the roles Supabase gives real callers. They need a local Postgres and
skip, loudly, without one.

```
npx vitest run tests/database
PEGASUS_RLS_MUTATE=1 npx vitest run tests/database/rls.test.ts   # must fail
```

`tests/contract/supabase*` and `tests/contract/rls-mutation*` need a real
Supabase project. They are gated on an explicit opt-in rather than on
credentials being present, because a run that quietly seeded somebody's project
because their `.env` happened to be loaded would be a nasty surprise.

```
PEGASUS_CONTRACT_DB=1 npx vitest run tests/contract
```

They seed two organisations with fixed ids, and the RLS mutation additionally
creates two auth users — `is_org_member` resolves membership through
`auth.uid()`, so a real session is the only way to prove RLS isolates. Both
tear down after themselves.

## Switching a deployment over

1. Apply `supabase/migrations/APPLY_0022_TO_0029.sql` in the SQL editor. It is
   guarded throughout and safe to re-run.
2. Confirm `NEXT_PUBLIC_SUPABASE_URL` and an anon/publishable key are set. That
   is what `appConfig.isMockData` reads, and it is the whole switch.
3. Seed the tenant. The TypeScript seed builds the demo workspace in memory and
   does not write to Postgres; `supabase/seed.sql` covers users, the
   organisation and members.

Until step 3, a configured deployment will serve empty screens rather than the
demo — which is correct, and is why the adapter throws on a failed read rather
than returning `[]`.
